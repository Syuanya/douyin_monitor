# 设置模块拆分与优化路线

## 拆分目标

设置模块的目标不是继续堆开关，而是形成稳定的“设置中心”架构：UI 只负责展示和反馈，服务层负责配置读写、校验、备份、导入导出、存储检查和运行时生效。

## 当前问题

- `app/ui/views/settings_view.py` 仍然偏重，但配置保存、校验、备份、运行时热更新已经开始向服务层迁移。
- 设置项数量较多，用户需要搜索、分组和明确反馈，否则很难判断应该修改哪里。
- 完整备份、完整恢复、开发模式、Cookie 健康清理等操作有覆盖或敏感信息风险，需要确认机制。
- Flet 页面控件较多，后续继续堆功能会增加灰色块、空白块和卡顿风险。

## 已落地架构

```text
app/ui/views/settings_view.py
    设置页 UI、控件收集、局部反馈、搜索过滤、未保存状态提示

app/core/ui_services/settings_service.py
    统一保存设置、重新加载最新配置、合并保存、保存 Cookie

app/core/ui_services/settings_validator.py
    统一校验数字范围、枚举、布尔项、开发模式覆盖逻辑

app/core/ui_services/settings_runtime_apply.py
    保存后让视频解析、Cookie 池、账号通知等可即时生效的配置生效

app/core/ui_services/settings_backup_service.py
    配置包、完整备份、脱敏备份、导入恢复

app/core/ui_services/settings_storage_service.py
    存储目录创建、可写性测试、磁盘空间检测、临时下载残留扫描与清理

app/core/ui_services/settings_cookie_service.py
    Cookie 池分析、脱敏展示、健康状态合并、重复/无效片段统计

app/core/ui_services/settings_proxy_service.py
    代理地址规范化、格式校验、连通性测试

app/core/ui_services/settings_preset_service.py
    稳定/标准/高速/开发诊断运行模式预设，只改表单、保存后生效
```

## P0：结构稳定性与保存安全

已完成：

- 新增 `settings_service.py`，统一处理配置保存流程。
- 新增 `settings_validator.py`，统一处理参数范围、非法值和开发模式覆盖逻辑。
- 新增 `settings_runtime_apply.py`，统一处理保存后的运行时生效。
- 新增 `settings_backup_service.py`，统一处理配置包、完整备份、脱敏备份、导入恢复。
- 新增 `settings_storage_service.py`，统一处理存储目录可写性和磁盘空间检查。
- `settings_view.py` 不再直接拼接完整配置和备份 ZIP，只收集控件值、调用服务、显示反馈。
- 保存前从磁盘重新加载最新 `user_settings.json`，再合并保存，降低旧页面状态覆盖其他配置的风险。
- 保存后会把自动修正后的值回填到控件，避免用户以为保存的是错误输入值。
- 开发模式开启时，按实际运行逻辑自动关闭全局限速、Cookie 冷却和风控退避。
- fallback 设置页已缩减为最小可用恢复页，只保留存储路径、Cookie、代理、保存和重新加载完整设置页。
- 保存按钮已增加 saving 状态和防重复点击保护。
- 设置页已增加未保存修改提示。

待继续：

- 离开设置页前拦截未保存修改，目前只做页面内提示。
- 进一步把设置页 UI 分区拆成独立组件。

## P1：用户交互体验

已完成：

- 增加设置搜索框，支持按 Cookie、代理、下载、并发、更新、备份等关键词过滤设置分组。
- 保存反馈继续保留变更摘要：变更数量、参数修正、即时生效、下次任务生效、Cookie 同步警告。
- 危险操作增加二次确认：完整备份、完整恢复、恢复配置备份、清理 Cookie 健康记录、首次开启开发模式。
- 长路径类提示继续控制为短文件名/短状态，不把完整路径直接塞进 SnackBar。
- 运行模式预设：稳定长期运行、标准日常使用、高速批量处理、开发诊断模式，只修改表单，保存后生效。

建议下一步：

- 设置页增加顶部或左侧二级导航：基础、存储、Cookie、解析下载、监控、备份、高级。
- 每组设置支持“恢复本组默认值”。
- 导入/恢复前展示将被覆盖的配置项预览。

## P2：核心能力补全

已完成：

- 存储检测：目录是否可创建、是否可写、剩余磁盘空间和总空间。
- 存储维护：扫描 `.tmp`、`.part`、`.download`、`.crdownload` 等临时下载残留，显示数量和占用空间。
- 临时残留清理：清理前二次确认，只删除明确的临时下载残留，不删除正常视频/图片文件。
- 脱敏备份：不包含 Cookie 和 web_auth 登录凭证，适合上传 GitHub 前自查。

已完成：

- Cookie 池分析：显示数量、格式可用数量、可疑 Cookie、重复/无效片段、冷却/禁用状态。
- Cookie 脱敏展示：只显示键名、长度和健康状态，不显示 Cookie 原文。
- Cookie 池测试：支持批量测试抖音 Cookie，避免只能测试第 1 个。
- 代理基础诊断：支持 HTTP/HTTPS/SOCKS5 地址格式校验、地址规范化、连通性测试。
- 运行模式预设：稳定、标准、高速、开发诊断四种推荐配置，降低用户手动调并发和风控参数的成本。

建议后续补齐：

- Cookie 池列表化管理：单独删除、禁用、上移/下移排序。
- 平台级代理策略：抖音直连、TikTok 走代理或相反。
- 更细粒度的缓存清理和失败下载记录清理。
- 备份恢复前预览。

## P3：Flet 稳定性与灰色块规避

已完成：

- fallback 页面不再渲染大量高级 Switch，降低完整设置页失败后的二次灰屏风险。
- 保存、检查目录、扫描残留、清理临时残留、Cookie 测试等反馈以局部文本为主，避免整页重绘。
- 设置页高级布尔项已从原生 `ft.Switch` 改为稳定的按钮式开关，统一由 `_toggle_values` 字典保存状态。
- 单账号通知列表已改为搜索 + 分页 + 批量开关，避免账号多时一次性挂载大量开关控件。
- 新增回归测试和静态检查，禁止设置页重新引入原生 `ft.Switch` 或 `TextField(expand=True)`。

建议最后做：

- 长路径、长 Cookie、长状态文本不要直接放到 SnackBar。
- 进一步把完整设置页拆成多个 section 组件，降低单文件和单页面重绘压力。
- 账号通知后续可继续补“仅重点账号”“按分组批量开关”等业务筛选。
